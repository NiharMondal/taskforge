## High — fix first

### Security

#### H1. Someone can take over an account before its owner first signs in with Google ✅
`apps/backend/src/modules/auth/auth.service.ts:166-188`

Registering never verifies the email, and Google sign-in links automatically to any existing account with the same email. So an attacker can register `victim@gmail.com` with their own password. When the victim later signs in with Google, they land in that account, and the attacker keeps password access to it.

**Fix:** when linking Google to an existing account whose email was never verified, delete the existing `EMAIL` sign-in row, or require the password first. Long term, add email verification.

> **Status: fixed (2026-10-27).** Added `User.emailVerifiedAt`, set by Google sign-up. Migration `20261027103815_add_user_email_verified_at` backfills every existing account as verified, so existing users see no change. Linking Google to an unverified account now deletes its `EMAIL` auth and marks the email verified, in one transaction.
>
> Still open:
> - Accounts that existed before the migration are trusted as verified (see the comment in the migration for the stricter backfill).
> - An attacker's already-issued token stays valid until it expires (≤1 day), because there is no way to revoke tokens.
> - Anything the attacker set up in the account before the link survives it, such as workspace members they invited.
>
> Real email verification at registration would close all three.

#### H2. A user may be able to overwrite or delete another user's avatar ✅ ⚠️
`apps/backend/src/cloudinary/cloudinary.service.ts:38-72`, `apps/backend/src/modules/user/user.service.ts:64-87`

- The client chooses the temp id.
- `promoteToPermanent` builds the permanent id by removing `/temp/` and renames with `overwrite: true`.
- `isTemp` only checks `includes("/temp/")`.

If the unsigned preset lets the uploader choose `public_id`, an attacker can upload to `taskforge/temp/user-avatar/<victim's id>`. Promotion then overwrites the victim's avatar, and the attacker's account now stores the victim's id. The attacker's next avatar change deletes the victim's file. ⚠️ This depends on the Cloudinary preset settings, which are not in the repo.

**Fix:**
- Build the permanent id on the server, e.g. `taskforge/user-avatar/<userId>/<random>`.
- Use `overwrite: false`.
- Require `startsWith("taskforge/temp/user-avatar/")`.

> **Status: fixed (2026-10-27).**
> - `CloudinaryService.promoteToPermanent(tempId, folder)` now renames to `<folder>/<uuid>` with `overwrite: false`; `UserService` passes `taskforge/user-avatar/<userId>`. The destination is never derived from the client's id.
> - `isTemp` now requires the `taskforge/temp/` prefix (backend and web), and a non-temp id is refused instead of adopted.
> - Existing avatars keep working; they move to the new layout the next time each user changes their avatar. No migration was needed.
> - Covered by the new `src/cloudinary/cloudinary.service.spec.ts`.
>
> Still open: `delete-temp` has no ownership check (see Low).

#### H3. MEMBERs can edit an issue's description ✅
`apps/backend/src/modules/issues/issue.service.ts:122-127`

The fields a MEMBER can't change are `title`, `priority`, `sprintId` and `assigneeId`. The list leaves out `description`. The spec (`apps/backend/spec/issue-spec.md`) and the frontend copy of the rule (`apps/web/src/features/memberships/lib/permissions.ts:39`) both say a MEMBER may only change the status.

**Fix:** switch to an allow-list: MEMBER may send only `status` and `rank`.

> **Status: fixed (2026-10-27), as part of workspace roles (PR 1 of 3).**
> - Issue writes are now checked field by field against an allow-list (`src/common/permissions/issue-access.ts`); a field not in the list is refused, so `description` can no longer slip through.
> - Rules are permissions on a per-workspace `Role` (migration `add_workspace_roles` seeds Owner/Admin/Member/Viewer into every workspace and points every membership and invitation at one). `RolesGuard`/`@Roles` are replaced by `@RequirePermission(...)`.
> - Deliberate change: a MEMBER may now create issues and edit all fields of issues they reported or are assigned to; still no DONE, no delete.
> - The web app still uses its own stricter copy of the rules until PR 2.

### Tenancy and data integrity

#### H4. Switching workspace briefly shows workspace B's data under workspace A ✅
`apps/web/src/features/workspace/context/workspace-context.tsx:67-71`

`setWorkspaceHeader(newId)` runs, then `queryClient.invalidateQueries()` runs synchronously. At that moment the active queries are still keyed to the old workspace (e.g. `["projects", oldWs]`). They refetch with the new `x-workspace-id`, so workspace B's data is stored under workspace A's key. Switching back briefly shows B's projects and roles.

**Fix:** remove the blanket invalidate, since the keys already include `workspaceId`. Better: have each `queryFn` send the `workspaceId` from its own query key as the header, instead of relying on a global mutable header.

> **Status: fixed (2026-10-27).**
> - Every workspace-scoped API function now takes `workspaceId` and sends it with `inWorkspace(workspaceId)`; the hooks pass the same id they key the cache by. A response can no longer be stored under another workspace's key.
> - The blanket `invalidateQueries()` on switch is gone.
> - The interceptor now reads the active workspace *before* awaiting the auth token, so even an unpinned request can't be re-targeted by a switch mid-flight.
> - Not verified in a browser yet.

#### H5. Dragged cards very likely don't keep their position ✅ ⚠️
`apps/web/src/features/issues/components/board/BoardView.tsx:207-247`

`handleDragEnd` calls `setActiveId(null)` first, then reads `newRank` and `positionChanged` from inside a `setColumns` updater. Because the component already has a pending update, React doesn't run that updater straight away; it runs it during the next render. So both values are still `undefined`/`false` when they are read:

- Reordering within a lane sends no PATCH.
- Moving to another lane sends only `{ status }`, so the backend appends the card to the bottom.

⚠️ Confirm in the browser.

**Fix:** compute `ordered`, `newRank` and `positionChanged` from the current `columns` outside the updater, then call `setColumns(ordered)`.

> **Status: fixed (2026-10-27).** `handleDragEnd` now computes the lane order and rank from `columns` before updating state (dnd-kit always calls the latest handler, so `columns` includes the mid-drag lane move). Also fixed the related Medium edge case: a neighbour with no rank no longer sends the card to the top of the lane; a same-lane move that can't get a rank now puts the lane back and says so, instead of showing a fake success. Not yet verified in a browser.

#### H6. The backend's rank order can disagree with the frontend's ⚠️
`apps/backend/src/modules/issues/issue.service.ts:210-214`, `apps/backend/scripts/backfill-issue-rank.ts:52-55`

`orderBy: { rank: "desc" }` uses the database's text sort order. Fractional-index keys need plain byte order, which is what the frontend uses (`apps/web/src/features/issues/lib/rank.ts:33`). Under an `en_US.UTF-8` database, "a0V" and "a0k" sort the other way round, so a card "appended to the end" can land mid-lane. ⚠️ Check the production database's collation.

**Fix:** a migration that sets `Issue.rank` to `COLLATE "C"`.

> **Status: fixed (2026-10-27).** Migration `20261027125000_issue_rank_byte_order` sets the column to `COLLATE "C"` (Prisma can't express collation, so it lives only in the migration; `prisma migrate dev` reports no drift). Confirmed the bug on the local `en_US.UTF-8` database first. Correction to the example above: appending only looks at a key's integer part, so `a0V`/`a0k` doesn't trigger it. The real case is a card dragged above the first one (key `Zz`): `en_US` sorted `Zz` after `a0`, so a new card got `a0` again — a duplicate rank. Covered by a new e2e test that fails without the migration and passes with it. The backfill script's `ORDER BY rank` is fixed by the same change.

#### H7. Two cards created at the same time in one lane get the same rank
`apps/backend/src/modules/issues/issue.service.ts:195, 205-223`

The code reads the highest rank, then writes, with no transaction or lock, and nothing makes `(projectId, status, rank)` unique. Once two neighbours share a rank, the client can't compute a key between them. The fallback for a corrupt stored key, `generateKeyBetween(null, null)`, returns `"a0"`, which can collide with an existing key.

**Fix:** a serializable transaction or advisory lock per lane, or a unique index plus a retry.

> **Status: fixed (2026-10-27).** Every server-computed rank (create, and a status change sent without a rank) now runs in a transaction holding `pg_advisory_xact_lock` on its `(project, status)` lane, so concurrent appends queue instead of reading the same last rank. Reproduced first: 8 parallel creates in one lane got only 2 distinct ranks; now they get 8 (new e2e test). The corrupt-key fallback now appends after the highest *valid* key in the lane instead of restarting at `"a0"`.
>
> Still open: ranks the *client* computes on drop are stored as sent, so two people dropping into exactly the same gap at the same moment can still collide. Rare; a unique index on `(projectId, status, rank)` plus a client retry would close it.

## Medium

### Backend

- **Login reveals whether an email is registered.** `auth.service.ts:104-117` answers 404 "User not found", 401 "Password is not set", or 401 "Invalid password". → Return one generic 401.
  - **Status: fixed (2026-10-27).** `signIn` now starts from the `EMAIL` `Auth` row (matched through its user's email, which lives on `User`) and returns one 401, "Invalid email or password", for an unknown email, a Google-only account and a wrong password. When nothing matches it still compares against a dummy bcrypt hash, so response time doesn't give it away either. The web login form already showed one generic message. Note: `POST /auth/register` still answers "Email already in use" — unavoidable without email verification.
- **Some errors return plain 500s without the `success: false` envelope.** `HttpExceptionFilter` only catches `HttpException`, and nothing maps Prisma's P2002 (duplicate) or P2025 (not found). `@IsOptional()` also lets `null` through, so `PATCH {"title": null}` reaches the database and returns 500. → Add a Prisma exception filter (P2002 → 409, P2025 → 404) and add `@ValidateIf(v => v !== null)` on non-nullable fields.
  - **Status: fixed (2026-10-27).** `HttpExceptionFilter` now catches everything: P2002/P2003 → 409, P2025 → 404, anything else → a logged 500 in the envelope that never echoes the raw error. Confirmed against the real DB that the pg driver adapter reports a duplicate as P2002. New `@IsOptionalNonNull()` replaces `@IsOptional()` on NOT NULL fields (issue title/status/priority, project/sprint/workspace/user name), so `{"title": null}` is a 400; nullable fields the web app clears with `null` (assignee, sprint, dates, goal) are unchanged.
- **Accepting an invitation isn't atomic.** In `invitation.service.ts:199-249` the PENDING check sits outside the transaction, so an invitation revoked in between still gets accepted. → Inside the transaction, use `updateMany({ where: { id, status: PENDING } })` and check the count.
  - **Status: fixed (2026-10-27).** The transaction now first claims the invitation with `updateMany({ id, token, status: PENDING, expiresAt > now })` and creates the membership only if exactly one row was claimed. Matching the token also stops an old link from accepting an invite that was re-sent (possibly with another role). Two simultaneous accepts now give one 201 and one clean 4xx, with one membership (e2e).
